록맨 에그제 2 한글패치 V0.9 - MENU362CAP 진단 빌드
===================================================

이 패키지는 정식 배포판이 아닙니다.
이번 빌드의 상한값(바이트)은 폴더 이름과 manifest.json 의
variant_details.cap_bytes 에 적혀 있고, 패치를 적용할 때 화면에도
표시됩니다.


지금까지의 결과
---------------

  00/352 + 00/362 포인터 되돌림  ->  메뉴 정상
  00/352 만 되돌림               ->  메뉴 멈춤
  00/362 만 되돌림               ->  메뉴 정상   (원인 확정)
  00/362 를 빈 공간으로 이동      ->  메뉴 멈춤   (주소·이웃 배제)
  00/362 엔트리를 원본 길이로 제한 ->  메뉴 정상

원인은 아카이브 00/362 의 엔트리 내용이고, 길이가 유력합니다.


아직 확정되지 않은 것
---------------------

"원본 길이로 제한" 빌드는 길이를 줄이는 동시에 해당 엔트리를 일본어로
되돌렸습니다. 따라서 길이가 문제인지, 특정 엔트리의 내용이 문제인지는
아직 갈리지 않았습니다.

또 "원본보다 길어진 엔트리"는 00/362 만의 문제가 아닙니다. raw 아카이브
224개 전부가 그런 엔트리를 갖고 있고(총 3,647개), 그중에는 한 엔트리가
201바이트에서 477바이트로 늘어난 것도 있는데 그것들은 멀쩡히 동작합니다.
그러므로 "원본보다 길다"는 것 자체는 방아쇠가 아닙니다.


이번 빌드가 하는 일
-------------------

00/362 를 다시 만들되, 한글 엔트리를 **상한값 이하일 때만** 유지하고
넘는 것만 일본어 원문으로 되돌립니다. 원본보다 길어도 상한 안에 들면
한글 그대로 둡니다.

00/362 의 엔트리 길이는 이렇습니다.

  원본  : 최대 15바이트
  한글판: 최대 43바이트

상한값을 15와 43 사이에서 옮겨 가며 시험하면, 메뉴가 견디는 실제
바이트 예산을 좁힐 수 있습니다. 만약 특정 엔트리 하나가 범인이라면
그 엔트리의 길이에서 결과가 갈리므로, 어느 쪽이든 범인의 길이가
드러납니다.

다시 만든 아카이브는 0x910000(패치가 건드리지 않은 0xFF 빈 공간)에
두고 포인터를 그쪽으로 돌립니다. 빌드할 때 그 자리가 정말 전부 0xFF
인지, 다시 만든 표가 스스로의 검사를 통과하는지 확인합니다.


적용 방법 (Windows)
-------------------

1. 이 ZIP을 새 폴더에 완전히 압축 해제합니다.
2. 보유한 깨끗한 일본판 Rev 1 ROM을 APPLY_PATCH.cmd 위로 끌어다 놓습니다.
3. SUCCESS 와 함께 이번 빌드의 상한값이 표시됩니다.
4. My Boy!에서 새로 부팅하고, 필드에서 움직일 수 있게 되면 START를
   누릅니다.

결과(열림 / 멈춤)를 알려주시면 다음 상한값을 정합니다.


화면에 보이는 것
----------------

상한을 넘은 엔트리는 일본어로, 나머지는 한글로 섞여 보입니다.
진단용이라 정상입니다.
